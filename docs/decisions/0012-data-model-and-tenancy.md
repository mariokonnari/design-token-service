# 0012. Data model, migrations and tenant isolation

- Status: Accepted
- Date: 2026-10-07
- Builds on: [0001](0001-monorepo-structure.md), [0003](0003-workspace-package-consumption.md), [0006](0006-token-subset-and-tier-rules.md)

## Context

`apps/api` was a placeholder with one liveness route. Phase 3a gives it a data layer: a Postgres schema with committed migrations, validated configuration, a real-database test harness, and a repository skeleton that makes cross-tenant access hard to write. There is no authentication, no HTTP routes beyond `/health` and `/ready`, and no deployment yet. Multiple teams ("organizations") will share one database, so the most important property is that one organization can never read or change another's rows.

## Decision

### Tools and versions

- **Postgres 17**, locally (`docker-compose.yml`, port 5433, named volume, healthcheck) and in CI (`postgres:17` service container). Supabase's default for new hosted projects appears to be 17 (the hosted default is **not confirmed from an official page**: only the self-hosted default change to 17, dated 2026-06-17, is documented). If the real project is created on another major, change one image tag.
- **Prisma 7.10.x**, installed with explicit `@7` ranges. npm's `latest` tag for `prisma` currently points to **8.0.0-rc.20, a release candidate**; the official release-status page says Prisma 8 is a release candidate and recommends staying on 7 for production. A plain `pnpm add prisma` would have installed the RC silently. The Prisma CLI also prints an "upgrade to latest" banner; ignore it. Revisit when 8.0.0 is generally available.
- **Prisma 7 specifics:** the `prisma-client` generator with a required `output` (`apps/api/src/generated/prisma`, **not committed**, regenerated by the `postinstall` script of `apps/api` and by CI); a **driver adapter** (`@prisma/adapter-pg` over `pg`) is required; configuration lives in `apps/api/prisma.config.ts`; `.env` files are not loaded by Prisma (the config loads one with Node's built-in `process.loadEnvFile()` for CLI use only, never in the API runtime); `prisma generate` does not run after `migrate`.
- **`prisma generate` evaluates `datasource.url`** and fails when `DATABASE_URL` is unset, which would break a fresh clone and the CI install. The config uses a clearly named placeholder URL **only for the `generate` command**; every other command (`migrate`, `studio`) still requires the real variable and fails without it. Verified both ways.
- **Prisma's install scripts are not run.** pnpm blocked `prisma@7.10.0` (preinstall) and `@prisma/engines@7.10.0` (postinstall) and made `pnpm install` exit 1 (`ERR_PNPM_IGNORED_BUILDS`). Tested with the scripts blocked: the CLI works, because it downloads the schema engine it needs on first use (the binary appeared when the CLI first ran). So no approval was needed, and the two packages are recorded as **explicitly ignored (`false`)** in `pnpm-workspace.yaml`, next to the existing `esbuild` entry, which makes install exit 0. **Unverified:** the same lazy download on Linux (CI); only CI itself can confirm it.
- **zod 4** for configuration (a dependency of `apps/api` only), **supertest** and **Vitest** for tests, `typescript` (6.x) as an explicit devDependency of `apps/api` for the convention test.

### Configuration and probes

- `src/config/env.ts` validates `process.env` once. **It fails closed:** `NODE_ENV` has no default (a missing value must not silently mean development) and `SESSION_SECRET` (at least 32 characters) has no default in any environment, which is stricter than "no default in production". One error lists **every** invalid variable and never prints a value. `SIGNUP_ENABLED` accepts only `true` or `false`; `ALLOWED_ORIGINS` is a comma-separated list of origins (no paths).
- Env files are loaded only by the dev script (`tsx watch --env-file=.env`). `start` and production load no file. `apps/api/.env.example` is committed; `.env` is gitignored (verified with `git check-ignore`).
- **The app does not connect to the database at startup.** `GET /health` is dependency-free liveness. `GET /ready` runs `SELECT 1` through a lazily created `pg` pool (2 s timeouts) and answers `503 {"status":"unavailable"}` with no error details when the database is unreachable. It recovers on its own when the database returns. The readiness probe uses `pg` directly (not the ORM) so it does not depend on the generated client.
- `scripts/smoke-api.mjs` passes **dummy** required variables (overriding anything inherited, so it can never touch a real database) and also asserts `/ready` is `503`. This is how CI's smoke test works with no database, and it was proven by running it with no `.env` file and no Postgres running.

### Data model

Six models, uuid primary keys generated by the **database** (`gen_random_uuid()`), so rows can be inserted with raw SQL and no sequential id ever appears in a URL:

| Model | Notes |
|---|---|
| `Organization` | `slug` unique, `name` |
| `User` | `email` unique and stored lowercase, `passwordHash`, `sessionVersion` (for invalidating sessions later) |
| `Membership` | user, organization, `role` (OWNER, EDITOR, VIEWER); unique per (user, organization) |
| `Brand` | belongs to an organization; `slug` unique per organization; `visibility` (PRIVATE default, PUBLIC); `draftRevision` |
| `Token` | one row per token: `path`, nullable `type`, `value` (jsonb), `version`; `path` unique per brand |
| `Release` | per brand `number` (from 1), `sourceRevision` (the `draftRevision` it was built from), `snapshot` (jsonb), `css` (text), `cssSha256`, `createdById` |

Table and column names are Prisma's defaults (quoted CamelCase), which is awkward in hand-written SQL but needs no mapping layer.

**Indexes.** A foreign key only needs its own index when no unique index already leads with that column. `Membership(userId)`, `Brand(organizationId)`, `Token(brandId)` and `Release(brandId)` are covered by their composite uniques; `Membership(organizationId)` and `Release(createdById)` get explicit indexes. A test checks that **every** foreign key column leads some index, so future tables cannot forget one.

**Delete rules.** Organization deletion is not an API feature in v1, so the rule is "refuse unless it is clearly safe":

| Relation | Rule | Why |
|---|---|---|
| Membership to User, Organization | CASCADE | a pure join row, meaningless alone |
| Brand to Organization | RESTRICT | never delete an organization's brands by accident |
| Token to Brand | CASCADE | tokens are the brand's mutable draft; releases hold the history |
| Release to Brand | RESTRICT | releases will become immutable published artifacts |
| Release to User (`createdById`) | RESTRICT | keep the audit trail |

Consequence: an organization or brand that has releases cannot be deleted without an explicit future purge process. That is intended.

### CHECK constraints (defense in depth)

`schema.prisma` cannot express CHECK constraints, so they are hand-written in the migration SQL and **named**, so tests assert which rule fired:

- `Organization_slug_format`, `Brand_slug_format`: `^[a-z0-9]+(-[a-z0-9]+)*$` (the same segment pattern as token paths; see ADR 0006).
- `Token_path_format`: the dotted form of that pattern.
- `User_email_lowercase`: `email = lower(email)`.
- `Token_type_supported`: `type IS NULL OR type IN ('color','dimension','fontFamily','fontWeight','number')`.
- `Token_type_null_only_for_alias`: `type` may be NULL only when `value` is an alias string (`jsonb_typeof(value) = 'string' AND (value #>> '{}') ~ '^\{[^{}]+\}$'`). **`Token.type` is nullable** because an alias token inherits its target's type in the tokens-core model, and a group's `$type` is already resolved into literals by `flatten`.
- `Release_number_positive` (`number > 0`) and `Release_cssSha256_format` (64 lowercase hex characters; an addition to the request).

Tests insert violating rows **directly with raw SQL** (125 tests), including the four `Token.type` cases written first and shown red: untyped alias accepted, untyped literal rejected, typed alias accepted, bad type rejected. A sync test compares the SQL type list with `TOKEN_TYPES` from tokens-core.

**Honest limit:** `prisma migrate diff` only compares what Prisma models. **It cannot see these constraints**, so removing one would not fail the drift check; the constraint tests are their only guard. The database does not normalize either: it rejects a mixed-case email, it does not lowercase it, so the application must.

### Migrations and drift

Migrations are committed. `pnpm db:drift` runs `prisma migrate diff --from-migrations ... --to-schema ... --exit-code` and must report no difference (CI runs it too); it was proven to fail (exit 2) when `schema.prisma` and the migrations disagree. Prisma 7 needs an explicit **shadow database** for this and for `migrate dev`: `<database>_shadow` on the same server (or `SHADOW_DATABASE_URL`), created on demand by `scripts/with-shadow-db.mjs`, which refuses any name that does not end in `_shadow` because Prisma wipes it.

### Tenancy: repository layer, TenantScope, lint rule

- **`src/tenancy/scope.ts`** defines `TenantScope` (`organizationId`, `userId`, `role`) and the single constructor `issueTenantScope`, intended for the future auth middleware after it has verified the session and the membership. **Guarantee, in two halves:** at compile time the type carries a brand whose symbol is not exported, so an object literal does not satisfy it; at run time every scope is frozen and registered in a private `WeakSet`, and `requireScope` (called by every repository method) rejects anything else, including a plain object, a JSON round trip, or a cast.
- **Limits.** A **spread copy** of a real scope *does* type-check (the brand survives a spread; the linter flagged an assertion as unnecessary), so the compile-time half is not airtight; the runtime check rejects it. The scope proves nothing about the membership being real: that is the auth middleware's job. Nothing stops a repository author from writing a query that ignores `scope.organizationId`.
- **Every repository function takes a `TenantScope` first and puts `organizationId` in every query** (`findFirst({ where: { id, organizationId } })`, never "fetch by id, then compare"). A brand from another organization is indistinguishable from one that does not exist. A malformed id is a plain "not found" (Postgres raises an error for non-uuid text, which must not become a 500).
- **`src/tenancy/policy.ts` is the one place roles are compared** (`canRead`, `canWrite`, `assertCanWrite` throwing a typed `ForbiddenError`). Repositories call it; none compares roles itself. Each role is tested.
- **A convention test** parses the repository sources with the TypeScript compiler API and asserts that every exported function and public method takes `TenantScope` first, calls `requireScope`, and mentions `organizationId` in every `this.db.<model>.<op>(...)` call. It asserts it inspected at least one function and has self-tests proving it flags deliberately bad samples. **The `organizationId` rule is a heuristic on source text:** it catches a forgotten filter, not a wrong one; the database tests are what prove a query is right.
- **ESLint** (`no-restricted-imports`) forbids importing the generated client, `@prisma/*` or `pg` anywhere in `apps/api/src` except `src/db` and `src/repositories` (tests, scripts and seed files live outside `src/`), and forbids importing `issueTenantScope` outside `src/auth`. Proven by deliberate violations that fired and were removed (a type-only import of `TenantScope` and `issueTenantScope` inside `src/auth` are correctly allowed).
- **Cross-tenant tests against real Postgres:** organization B's scope reading organization A's brand returns `null` while A reads it; each side lists only its own; a smuggled `organizationId` in the input is ignored; breaking the filter on purpose failed both the database test and the convention test.

### Test harness

- API tests run against a **separate database whose name ends in `_test`** (`dts_test`), created and migrated by a Vitest `globalSetup`. **Test files run serially** (`fileParallelism: false`) because they share one database and truncate every table between tests: files in parallel would delete each other's rows mid-test. The cost is speed.
- **A guard refuses to run** unless `DATABASE_URL` points at a database whose name ends in `_test` (and is a safe identifier), and the truncate helper re-checks the database the connection **really reached** (`current_database()`). Both are tested. Proven end to end: the suite pointed at the dev database was refused and a sentinel row there survived.
- When Postgres is down, the setup fails with `Postgres is not reachable at localhost:5433 (ECONNREFUSED). Start the local database first: run pnpm db:up.` instead of a raw connection error.
- `pnpm test` now **needs the database running** (`pnpm db:up`). CI provides a service container.

## Alternatives considered

- **A user belongs to exactly one organization.** Simpler, but real teams overlap (a contractor in two organizations, a person who is OWNER of one and VIEWER of another). A `Membership` join with a role costs one table and one unique constraint and avoids a migration later. Chosen: memberships.
- **How the organization is chosen on a request.** Hidden session state ("current organization") makes requests ambiguous and cross-tab bugs likely. Decision: the organization is **explicit in the URL path**, and the auth middleware resolves the membership for exactly that organization and issues the scope. Whether it appears as a uuid or a slug is left to the routes phase; both are unique and indexed. A user who is not a member gets the same answer as for a missing organization.
- **Tokens as one JSON document per brand.** Atomic and trivial to snapshot, but no per-token constraints, no per-token version or conflict handling, and every edit rewrites the whole document. Chosen: **one row per token** in the draft; **JSON snapshots only for releases**, where atomicity and immutability are the point. Cost: assembling the tree from rows on every read.
- **Draft must always be valid vs may be invalid.** An editor passes through invalid states (a half-typed alias, a cycle while rewiring). Rejecting them would make editing impossible, so **the draft may be invalid**: the database enforces only shape-level rules (path format, supported type, alias-or-typed), and tokens-core validation (`resolve`, `checkTiers`) runs on demand and as a gate when **creating a release**. Cost: invalid drafts exist and the user must be shown the issues.
- **Immutable release snapshots with the generated CSS stored.** Storing the snapshot, the CSS and its hash makes a release reproducible and verifiable even after the exporter changes. Cost: storage, and **immutability is not yet enforced by the database** (no trigger or revoked privilege): in v1 only the application is trusted never to update a release; `RESTRICT` deletes protect against removal, not edits. A trigger is a candidate for a later phase.
- **Repository layer + TenantScope + lint rule (chosen)** vs a **Prisma client extension** that injects the organization filter into every query automatically (invisible magic, hard to test, easy to bypass with raw queries, and still no database backstop), vs **Postgres row-level security**, vs **schema-per-tenant**.
- **Why RLS is not used in v1.** RLS would add a backstop inside the database: even a query that forgets the filter returns nothing. It was not adopted because (1) the app connects through a pooler and a driver adapter, and the tenant must be passed per request with `SET LOCAL` inside a transaction, which Prisma does not do for you and which complicates every read; (2) a connection role that owns the tables or is a superuser bypasses RLS silently, so it only helps with a separate low-privilege role and careful grants; (3) it multiplies the test matrix (every policy, every role); and (4) the foundation and the conventions had to exist first. **What that costs:** there is no database-level backstop. A missed `organizationId` filter, a wrong one, or a cast that forges a scope would leak across tenants, and only tests, the lint rule, the convention test and code review stand in the way. Revisit RLS before production data is real.
- **Schema-per-tenant:** strong isolation and per-tenant dumps, but migrations must run once per tenant, connection and catalog overhead grows with tenants, and cross-tenant queries (admin, billing) get harder. Not worth it at this scale.
- **404, not 403, across tenants.** Reading another organization's resource returns "not found", so the response does not reveal that the resource exists. A 403 is only for a caller who is inside their own organization but whose role does not allow the action (`ForbiddenError`), where existence is already known.

## Consequences

- **Deployment risks to verify in Phase 6 (untested assumptions):** (1) the **Supabase pooler in transaction mode** with Prisma 7's `pg` adapter (prepared statements, `SET` and advisory locks behave differently behind a transaction pooler, and migrations need a **direct** connection while the runtime uses the pooled one); (2) **IPv4 versus IPv6 connectivity from Render** to Supabase (the direct host may be IPv6-only; the pooler is the IPv4-friendly route). Nothing here has been run against Supabase or Render.
- **Postgres 17 matches Supabase only if the assumption above is right.** Prisma 8 is not used until it is generally available.
- **Unverified here:** that Prisma's lazy engine download works on the Linux CI runner (only CI can show it); behavior under a connection pooler; behavior under concurrent load (tests run serially).
- **Every test run needs Docker** (locally) and a service container (CI). A developer who runs `pnpm test` without `pnpm db:up` gets the readable "run pnpm db:up" message.
- **The migration drift check has a blind spot** (CHECK constraints) covered only by tests; **release immutability is not enforced by the database**; there is **no database-level tenant backstop** (RLS); and the `organizationId` convention check is a text heuristic.
- **Timestamps** use Prisma's defaults (`timestamp(3)` without time zone, written in UTC); there is no pagination on `list` yet; string length limits exist only in the application (the brand `name`); password hashing and the session design are still to be decided (`passwordHash` and `sessionVersion` are placeholders for that phase).
- **uuid v4 ids** are random, so inserts scatter across the index; acceptable now, and uuid v7 or similar can be considered if write volume grows.
